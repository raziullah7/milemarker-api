# Report QA-1: adversarial review of the backend runtime

Reviewed: `next` at 8edd8e1, against 786f041. I built none of it. Live attacks ran on the end-to-end stack (its `ROUTING_SERVERS` checked: `http://fake-osrm:5000/...` only) and on a separate scratch Compose project with its own volumes and ports, also on the stand-in. No request reached a public routing server. Code experiments ran in scratch copies of the repository outside it, with the original environment's Python and `PYTHONPATH` pointing at the copy; the unmodified copy passes the whole suite (567 passed, 126 s).

## Attacked and found sound

- **Redis stopped while requests were in flight.** 2,882 requests over 90 s from six threads, all 200. Both workers fell back at once (connection refused), each with one WARNING. At the 30-second try, the stopped container's name was slow to fail: each worker's health took 0.405 s, the slowest answer of the drill. Redis was started at 45.6 s; the workers returned at the next try, 68.8 s, each with one INFO line, and health followed on each worker (`redis`, then `fallback`, then `redis`).
- **Redis paused.** 2,714 requests, all 200. Each call in flight timed out at 0.25 s; the slowest answer took 0.266 s. One warning per worker. No in-memory copy was served after the return: answers were rebuilt from the road in Redis (`routing_calls` 0, `cache_hit` false). Each worker had 31 to 33 threads before the drills and 43 after both; file descriptors stayed at 14. I saw no leak; the pool is capped at 8.
- **Keys.** Every part of the answer key is bounded: the labels come from the places table, the coordinates have 4 decimals, and `stop_cost` has at most 2 decimals up to 100. The only part a client can shape is the throttle's client address, and only when a proxy is trusted (Q1-13). A raised version and a changed fingerprint are each caught by a test (attack 4), and the live reload behaved as designed (Q1-12).
- **The rate limit, sequentially.** 60, then 429, across both workers. A forged `X-Forwarded-For` is ignored at 0. The schema and docs addresses answer 429 in JSON with `Retry-After`. Health was never limited (over 5,000 requests from one client in the two drills).
- **Start-up**, on a scratch Compose project with a fresh volume and no `.env`. The order was `db` healthy, `setup` exiting 0, then `api`, in 12.6 s. A second `up` reran `setup` while the API ran, and left 6,626 rows, 6,626 distinct IDs. A `setup` pointed at a database that does not exist made Compose exit 1, with `api` left Created. With Redis stopped before the API started, health said `fallback` and each worker logged one warning.
- **Shutdown.** The stand-in was paused and the API stopped 1 s into a request: the request finished (502 `routing_unavailable` at 5.04 s) before the master exited. `compose stop` took 4.95 s.
- **A worker that dies.** I sent SIGKILL to both workers while requests waited on them. Those requests were cut with no answer, a closed connection, which nginx will turn into `api_unavailable` in Phase 12. The master booted two new workers, and health answered 200 within 4 s.
- **Debug on.** With `DJANGO_DEBUG=1`, every error probed stayed JSON with no traceback: 404, 405, a foreign host, an unknown place, a bad `stop_cost`, and odd schema parameters and `Accept` headers. The exception is gunicorn's own refusals (Q1-05). A `Host` with a port matches on its name; an `ALLOWED_HOSTS` entry with a port never matches; `*` accepts any host.
- **The deployment check.** `check --deploy --fail-level WARNING` passes in the container. W018 appears with debug on, and W009 with a short key. The three reasons for the silenced checks are true: no cookies, sessions or forms; TLS belongs to the terminator (D-23).
- **The image.** It runs as uid 999 `app`. `/app` is owned by root and cannot be written; `app` can write only `/tmp`, `/var/tmp`, `/run/lock` and its home. There are no tests, scripts, documents (apart from `data/README.md`), uv, compiler or dev tools in it. The venv does not include system site packages. Redis's digest matches the pin.
- **Regressions.** The verifier and the regression pins pass (`tests/test_verify.py tests/test_regression.py`, 115 passed); the slow exactness test passes; the whole suite passes. In the diff, the planner now reads the station index before the answer cache, as ruled, and the planning code is otherwise unchanged.

## Not checked, and why

- **`down -v` on the shared project** was refused by the permission layer, because it deletes the stack's database volume. I ran the same start from a fresh volume as a separate scratch Compose project, and removed it and its volume afterwards.
- **The Python base image's digest** is not in the local image store under that reference, so I could not compare it without asking the registry.
- **The Postman collection (Newman)** needs a download through `npx`; not run.
- **Twenty repeats answered by both workers.** Sequential requests all landed on one worker; the cross-worker hit rests on CA-01 and on the drills, where both workers read the same keys.
- **The split between workers after a reload and one worker's restart** (Q1-12) is from reading only.
- **Phase 12 matters** (nginx, the network with no route out, `api_unavailable`) are out of scope, beyond the two hand-overs in Q1-05 and Q1-13.
